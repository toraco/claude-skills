# レビュー指摘の重大度基準

`local-review` と `auto-fix-review`（mention モードの依頼文）が共通で使う、🔴 / 🟡 / 🟢 の判断基準。各 skill 本文から参照される（skill としては発動しない）。

重大度は **影響の大きさ** で決める。どの観点（バグスキャン・CLAUDE.md・git 履歴など）で見つけたかでは決めない。プロジェクト固有の規約（TDD / Tidy First、ドキュメント更新の要否、レイヤー構成など）は、各リポジトリの CLAUDE.md と設計ドキュメントから読む。

`auto-fix-review` の mention モードの依頼文（Step 1-R）には、この基準の要約を直接書いている。Actions 上のレビュアーはこのファイルを読めないためである。基準を変えたら、依頼文の要約も合わせて直すこと。

## 🔴 バグ: マージすると実害が出るもの

次のどれかに当たり、**どんな入力・状態で何が壊れるかを具体的に書ける** もの。

- 現実にありうる入力・状態で、誤った結果・例外・クラッシュが起きる
- データの消失・破損・二重登録、トランザクションの不整合
- 悪用できるセキュリティの穴（認可漏れ、インジェクション、機密情報の漏えい）
- 過去の修正を巻き戻している（git 履歴で確認できるもの）
- 既存の呼び出し元・API の利用者・DB マイグレーションとの互換性を壊す
- 変更した振る舞いを確かめるはずのテストが、実際には何も確かめていない（常に通るなど）

## 🟡 設計上の問題: 今は壊れないが、直さずにマージすべきでないもの

次のどれかに当たり、**根拠を示せる** もの。根拠は、CLAUDE.md や設計ドキュメントの該当箇所の引用か、放置したときに起きることの具体的な説明のどちらか。

- CLAUDE.md や設計ドキュメントに **明記された** 規約への違反（例: 構造の変更と振る舞いの変更が同じ commit に混ざっている、必要なドキュメントの更新がない、レイヤーの依存方向に反している）
- 振る舞いを変えたのに、それを確かめるテストがない
- 現実的なデータ量で問題になるパフォーマンス（N+1 クエリ、上限のない取得、ループ内の I/O など）
- 今すぐは悪用できないが、防御が弱くなっている（入力検証の抜け、権限確認を呼び出し元任せにしている）
- 同じ情報の正本が 2 か所にできる、責務が別の層に漏れているなど、近いうちにバグを生む構造

## 🟢 指摘・改善提案: 直さなくてもマージしてよいもの

- 命名・読みやすさ・コメントの改善
- 必須ではないリファクタリングや置き場所の提案
- 起きるか不確かな懸念、本番で確認すればよい事項

## 指摘しないもの

- lint・型チェック・フォーマッタ・テストで機械的に見つかるもの
- 差分の外にある、もともとあった問題
- PR の目的そのものである、意図した振る舞いの変更

## 迷ったときのルール

- 2 つの重大度で迷ったら **低いほう** にする（🟡 を広げすぎると、修正ループが終わらなくなる）
- 🔴 で壊れ方を具体的に書けないものは 🟡 に、🟡 で根拠を示せないものは 🟢 に下げる

## 出力フォーマット

`/fix-review` Step 2-1 の解析ルールに合わせる。指摘が 1 件も無い重大度の見出しは出力しない。

```
### 🔴 バグ
#### 1. <指摘タイトル>
**ファイル:** `path/to/file.ext:<line>`
<問題の説明と修正案>

### 🟡 設計上の問題
#### 2. <指摘タイトル>
...

### 🟢 指摘・改善提案
#### 3. <指摘タイトル>
...
```

指摘が 1 件も無い場合は `### ✅ 指摘なし` とだけ出力する。
