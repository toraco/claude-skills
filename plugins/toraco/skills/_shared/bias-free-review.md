# バイアス排除レビュー 共通方法論

`revise-spec` / `revise-tests` など、「バイアス排除された subagent に独立に読ませ、親 skill が突合する」系 skill の共通規約。各 skill 本文から参照される（skill としては発動しない）。方法論の出自は `empirical-prompt-tuning`（書き手は自分の文章を客観視できない、という原則）。

## Subagent dispatch の原則

- スキャン系（読解・抽出）: `subagent_type: "Explore"`、`model: "sonnet"` を明示
- scoring / 分類系: `subagent_type: "Explore"`、`model: "haiku"` を明示
- **全ての Agent 呼び出しで `model` を明示する**（未指定だと品質差が出る）
- Agent はセッション継続できない。再スキャンは毎回、同じプロンプト・同じ設定で新規呼び出しする
- Agent Teams は使わない。並列化は skill 内からの Agent ツール並列呼び出しで行う

## バイアス排除の禁止指示

- subagent には「反対側の情報源を読むな」と **明示的に禁止** する（例: 実装アナリストに「仕様書・テストファイルを Read しないこと」）。「読まない方針で」のような弱い指示では Explore 系 agent は周辺ファイルを読みに行きバイアスが混入する
- 1 つの subagent に複数面（仕様と実装、実装とテスト等）を同時に読ませない。整合的に解釈してしまい drift / 差分が埋もれる
- **突合の主体は親 skill**。ペアリングと一次判定は親 skill が行い、scoring subagent には 1 件ずつ渡して分類だけ任せる

## Scoring の並列化ルール

- 1 項目につき 1 subagent（複数項目をまとめて渡すと分類にバイアスが混入するため禁止）
- 件数が 10 件未満: 全件を 1 メッセージ内で並列 dispatch
- 10 件以上: 5 件ずつのバッチに分け、バッチ内は並列・バッチ間は直列の順次パイプラインで進める

## confidence の表示規則

- `classification = out-of-scope` かつ `confidence < 50`: 最終表から除外し、最終レポートにも残さない（ノイズ削減）
- `classification != out-of-scope` かつ `confidence < 50`: 表には残すが、サマリ末尾に `(conf=XX)` を併記して低信頼であることをユーザーが認識できるようにする。分類を信じず再考する余地を残す
- `SKIPPED_ITEMS` に含まれる id（前周でスキップ済み）は表・ユーザー確認から除外し、再度聞かない

## Step 0 の自動確定（引数省略時のデフォルト）

対象・Mode・diff 範囲などの **前提条件** は、引数で明示されなければ自動判定結果を **そのままデフォルトとして採用** し、`AskUserQuestion` は発行しない。実運用ではほぼ常に推奨値が選ばれるため、確認の往復がコストに見合わない。

- 引数で明示された値は常に自動判定より優先する
- 自動確定した内容は Step 1 に進む前に **1 ブロックで必ず提示** する（採用値 + 採用理由 + 採用しなかった他候補）。ユーザーが「違う」と気づいて中断できる状態を作ることが、確認質問の代替になる
- 次の「自動確定できないケース」に限り `AskUserQuestion` にフォールバックする:
  - 候補が 0 件（対象仕様が 1 つも見つからない等）
  - `git` の default branch が検出できない / diff 範囲が空
  - 引数で指定されたパスが存在しない
- `--interactive` が指定されたときのみ、従来通り Step 0 の各項目を `AskUserQuestion` で確認する
- 指摘への対応方針（各 skill の Step 3）の扱いは次節「Step 3 の推奨方針の自動採用」に従う

## Step 3 の推奨方針の自動採用

実運用では Step 3 でも推奨（Recommended）の方針がほぼそのまま選ばれるため、**推奨方針が明確な項目は質問せずに自動採用** し、ユーザーに問うのは本当に判断が割れる項目だけに絞る。

### 自動採用 / 質問の振り分け（既定）

| 項目 | 扱い |
|---|---|
| 分類 ≠ decision-needed かつ `confidence >= 70` | **自動採用**。分類に対応する既定アクション（各 skill の Step 3 に定義）を実行する |
| 分類 ≠ decision-needed かつ `confidence < 70` | 質問する。分類の既定アクションを先頭に `(Recommended)` 付きで置く |
| decision-needed（🟣） | 質問する。scoring の `recommended_option` を先頭に `(Recommended)` 付きで置く |

- 質問する項目は **1 回の `AskUserQuestion` 呼び出しにまとめる**（1 呼び出しあたり最大 4 questions。5 件以上なら複数回に分けるが、各回で最大数を詰める）
- 自動採用した項目は、編集に入る前に **1 ブロックで必ず提示** する（id / 分類 / 信頼度 / 採用アクション / サマリ）。Step 0 と同じく、提示が確認質問の代替になる。編集は commit しないので、違っていれば `git diff` / `git checkout -- <file>` でユーザーがいつでも戻せる
- 自動採用したことで 1 件も質問が残らない場合は、`AskUserQuestion` を発行せずにそのまま編集へ進む

### フラグによる切り替え

- `--yes`: **一切質問しない**。低信頼項目は分類の既定アクションを、🟣 は `recommended_option` を採用する。`recommended_option` が無い 🟣 は採用せず「未決定」として最終レポートに残す（`SKIPPED_ITEMS` には入れない。次回また提示される）
- `--interactive`: 従来通り **全件を質問** する（Step 0 の確認も含む）。各質問では推奨を先頭に `(Recommended)` 付きで置く
- 両方指定された場合は `--interactive` を優先する

### 自動採用後の再確認をしない

- 「このファイルは大きく変わるが進めて良いか」のような **編集直前の再確認は行わない**。代わりに、大規模変更（節の全書き換え・describe 階層の組み替え等）になったファイルは最終レポートで明示し、差分を確認するよう促す
- 最終整合性確認で指摘が減っていない場合も **続行可否は問わず**、状況を最終レポートに警告として載せて終了する

## AskUserQuestion の運用

- ハーネス制約により 1 question あたり **最大 4 options**。5 候補以上になる場合は「上位 3 候補 + Other (手入力)」の 4 件に圧縮する
- 「1 質問あたり最大 4 件」の「件」は指摘 1 件（1 question）単位。分類をまたいだ混合は OK。4 件超は複数 question に分割する

## Tidy First（編集スコープ）

- skill が編集してよいのは対象側（revise-spec なら仕様ファイル、revise-tests ならテストファイル）のみ
- 反対側の修正が必要な項目は `HANDOFF_LIST` に積み、最終レポートで受け渡す（実装側 → `bugfix` / `local-review`、仕様側 → `revise-spec`）
- **commit / push は行わない**。必要なら `/commit` の利用を案内する

## git 範囲指定の `..` と `...`

- コミット一覧の取得（Mode 判定等）: `git log origin/<default>..HEAD`（**二点** = 分岐後のコミット一覧）
- diff 範囲: `origin/<default>...HEAD`（**三点** = マージベース基準の差分）
- 意味が異なるので誤って統一しないこと

## 共通 Red flags

| 出てくる合理化 | 実態 |
|---|---|
| 「自分で読み返せば十分」 | 書き手バイアスで問題が見えなくなっている。必ず subagent を dispatch する。 |
| 「1 つの subagent に両面を読ませれば速い」 | 整合的に解釈してしまい差分が埋もれる。必ず面を分離する。 |
| 「scoring を省略して自分で分類すれば速い」 | 分類の判断にもバイアスが入る。haiku でも良いので別 agent に通す。 |
| 「対象外側もまとめて直してしまおう」 | Tidy First 違反。編集は対象側のみ、反対側は `HANDOFF_LIST` へ。 |
| 「最終整合性確認をスキップ」 | 更新で新たな矛盾・破壊を生んでも気づかない。軽量でよいので必ず再確認する。 |
| 「念のため Step 0 で対象と Mode を確認しておこう」 | 自動判定が成立しているなら確認は不要。採用値を提示して進み、止まるのは候補 0 件 / diff 空 / `--interactive` のときだけ。 |
| 「🟣 も推奨があるから `--yes` 無しで自動採用しよう」 | decision-needed は判断が割れると scoring が判定した項目。既定では必ず問う。自動採用は `--yes` 指定時のみ。 |
| 「自動採用したので一覧の提示も省いて良い」 | 提示が確認質問の代替になっている。省くとユーザーが誤った採用に気づけない。 |
| 「念のため高信頼の項目も確認しておこう」 | 推奨がほぼそのまま選ばれる項目を問うのは往復コストに見合わない。質問は低信頼 / 🟣 だけに絞る。 |
