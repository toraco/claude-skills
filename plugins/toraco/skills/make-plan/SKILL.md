# 機能実装プランニング

**使い方**: `/make-plan <機能の説明>`

対象機能: $ARGUMENTS

以下のステップを実行し、実装計画を立案する。

## Step 1: 基本設計書／仕様ドキュメントの確認（What: 機能仕様・要件定義）

扱う対象は「機能仕様・要件定義（ユーザー向けの What）」。`docs/specs/`, `docs/requirements/` など、**何を作るか** が書かれたドキュメント。実装パターン・アーキテクチャ規約は Step 3 で扱うためここでは対象外。

プロジェクト内に基本設計書・仕様書・要件定義などのドキュメントが存在する場合は、最初にそれらを確認し、対象機能が既存のどの項目に該当するかを特定する。

該当項目が **存在しない** 場合は、ドキュメント側の更新も計画の一部となる。Step 2 の影響レイヤー列挙で `Docs` に該当セクション追記を含めること。

ドキュメントが見つからない場合は、ユーザーに所在を確認するか、コードから既存仕様を読み取る旨を明示する。

## Step 2: 要件分析

1. 機能の目的を明確化
2. 影響レイヤーを特定（該当するものを列挙。例: DB / Domain / Usecase / Infrastructure / API Routes / Frontend / Docs / Tests など、プロジェクト構成に応じて調整）
3. 類似・依存する既存機能を特定
4. **デザイン参照 URL の確認**: フロントエンド実装を含む場合、または API 実装であってもフロントエンドから呼び出される想定の場合は、ユーザーに Figma 等のデザイン URL を求める

不明な点があればユーザーに質問する。大きな仮定を置いて進めないこと。ただし計画立案の途中で作業を中断せず、以下の方針で扱う:

- **小さな仮定**（既存規約から推論可能なもの、例: 命名規則、既存との一貫性）は仮定を明示した上でドラフトを続ける
- **設計判断に影響する大きな不明点**（要件の根幹・業務ルール・UI デザイン詳細）は計画書末尾の **「ユーザーへの確認事項」** 節に番号付きで集約して提示する
- 仮定（こちらの提案）と確認事項（要決定）を必ず区別して明示する

## Step 3: 開発設計書・アーキテクチャドキュメントの確認（How: 実装パターン・アーキテクチャ規約）

扱う対象は「実装パターン・アーキテクチャ規約（開発者向けの How）」。`docs/architecture/`, `docs/frontend/`, `docs/testing/` など、**どう作るか** が書かれたドキュメント。機能仕様は Step 1 で扱うためここでは対象外。

関連する開発設計書・アーキテクチャドキュメントを **コード調査の前に** 読み、実装パターンを把握する。

プロジェクト内にある該当ドキュメントを探索する（例）:

- **API / バックエンド**: アーキテクチャ、レイヤー構造、エラーハンドリング、新規リソース追加手順
- **テスト**: Mock パターン、Fixture、新規テスト追加手順
- **フロントエンド**: Component パターン、データ取得層、状態管理 ...etc

ドキュメントの状況に応じて出力を分岐する:

- **存在し十分**: 関連箇所を引用・要約して計画書に記載し、本機能での適用方針を述べる
- **存在するが薄い**: 記載されている範囲を引用した上で、不足する観点（下記リスト参照）は Step 4 の既存コード調査で補う旨を明示する
- **該当ドキュメント無し**: 計画書に「パターン抽出対象の観点リスト」を列挙し、Step 4 で各観点を既存コードから抽出する方針を明示する

パターン抽出対象の観点（プロジェクト構成に応じて取捨選択）:

- ルーティング／ハンドラの書き方、レスポンス JSON 形
- エラーハンドリング（try/catch の扱い、エラー型の分類、HTTP ステータスマッピング）
- バリデーション層の有無と使用ライブラリ
- DB クエリ／トランザクションの書き方
- DI 配線・クライアント共有の方法
- テストのフィクスチャ／Mock 方針
- フロントエンドの Component／データ取得／状態管理パターン

## Step 4: 既存コードの調査

設計書で把握したパターン（または既存コードから抽出したパターン）を前提に、関連する既存コードを読む。プロジェクト構成に応じて対象を調整する。例えば:

- **DB スキーマ**: 関連モデル、リレーション、enum / 型定義
- **バックエンド**: エンティティ、ユースケース、ルーティング、スキーマ定義、DI 設定
- **フロントエンド**: 類似ページ、フォームコンポーネント、データ取得層、ルーティング
- **ドキュメント**: 類似機能の仕様書

## Step 5: 設計方針の決定

- **データモデル**: テーブル追加・変更、マイグレーション戦略
- **API**: エンドポイント URL、リクエスト/レスポンス概要、エラーケース
- **ドメイン**: エンティティ変更、ドメインエラー、バリデーションルール
- **フロントエンド**: ファイル構成、データフロー、状態管理、UI コンポーネント

（プロジェクトが扱わないレイヤーは省略してよい）

## Step 6: レビューチェックリスト

汎用的に発生しがちな指摘項目。全項目について **個別に** 判定し、以下の表形式で明示する（カラム構成・フォーマットはこの例に倣う）:

| # | 項目 | 判定 | 対策 / 理由 |
|---|---|---|---|
| 1 | DRY | 該当あり | 既存の `normalizeX` ヘルパを再利用する |
| 2 | 型の一貫性 | 該当なし | 新規型定義を伴わない変更のため |
| 3 | バリデーション漏れ | 部分的 | 入力側は zod で対応。ドメイン層の整合性チェックは既存 `validateX` で既にカバー済み |

判定ラベルは以下の 3 値のいずれかを使う:

- **該当あり**: 対象機能の実装範囲内でその懸念が発生しうる。対策を具体的に記述する（「既存の X でカバー済み」等の確認も対策として OK）
- **該当なし**: 対象機能の実装範囲内では物理的に発生しえない（例: フロントエンド関連の懸念を純バックエンド機能で判定するケース）。1 行で理由を添える
- **部分的**: 該当する範囲と非該当の範囲が混在する。該当部分への対策と、非該当部分の理由を併記する

「該当ありだが対策不要」という第 4 のラベルは作らない。発生しうるなら必ず何らかの対策を記述する。項目ごとのスキップ禁止。

チェック項目:

- [ ] **DRY**: 既存の共通ユーティリティ・ドメインサービスに再利用可能なロジックはないか
- [ ] **型の一貫性**: 既存の enum / 型で代用できないか（不要な新規定義を避ける）
- [ ] **API 仕様の重複**: 仕様書に OpenAPI 等で一元管理されるべき情報（エンドポイント URL、JSON スキーマ、ステータスコード詳細）を重複記載していないか
  - 前提: 一元管理ドキュメント（OpenAPI / schema.yaml / 仕様書等）が **プロジェクトに存在する場合のみ** 該当判定の対象。存在しない場合は「該当なし（一元管理ドキュメント未整備）」で良い。未整備プロジェクトへの OpenAPI 導入推奨は別タスクとして扱い、本チェックには含めない
  - 計画書自体は設計議論用であり仕様の一次ソースではない。計画書に JSON 例やエンドポイント仕様を書くこと自体は重複に該当しない。判定対象は「仕様ドキュメント（`docs/specs/` 等）側への重複記載」
- [ ] **命名の一貫性**: 既存の命名規則に従っているか
- [ ] **バリデーション漏れ**: クロスフィールドバリデーション、ドメイン層の整合性チェックに漏れがないか
- [ ] **パフォーマンス**: 不要な再レンダリング（メモ化の要否）、N+1 クエリ、過剰なデータ取得などの懸念はないか
- [ ] **既存パターン遵守**: ファイル配置・コード構造が類似機能と一致しているか
